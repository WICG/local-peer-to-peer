1. Introduction

This section is non-normative.

The Local Peer-to-Peer API aims to give browsers the means to communicate directly, without the aid of a server in the middle. It is designed to enable this communication within the confines of a local communication medium.

Many modern Web security measures rely on the presence of naming, signaling and certificate authorities. Local use-cases where these authorities are not readily available have started lagging behind in user experience or are not supported altogether. The Local Peer-to-Peer API aims to bring back first-class support for local communication use-cases while working within the same strict user-friendliness, security and privacy requirements.

Examples of potential uses of this API include: Collaboration tools that work during an internet outage or emergency situations, connecting to your NAS, your home security system, your robotic assistant doing the dishes or your GPU farm in the basement that’s running your personalized virtual assistant. See also Use Cases.

This specification aims to strike a balance between creating a powerful new building block for developers and providing a seamless, secure and privacy preserving experience for browser users. As an example: while the API doesn’t provide raw socket access, it does aim to give developers the flexibility to innovate on top by providing a persistent, two-way communication channel with little overhead.

The API is designed to be backed by an authenticated, streams-based transport. It is defined against the abstract operations of § 5 Transport abstraction, which a transport binding maps onto a concrete protocol. As a commitment to an open standards-based implementation path, this specification defines a binding to the Open Screen Network Protocol in § 12 Binding to the Open Screen Network Protocol. Other bindings are anticipated, for example WebTransport over QUIC with peers authenticated on the local network as explored by the IETF SETTLE working group.

2. Terminology

The term local communication medium refers to a communication medium that provides a local, direct communication channel between the communicating devices. It carries IP between the devices, directly or through a local network, for example a wired or wireless local area network or Wi-Fi Direct. Discovery and authentication may also use other channels, such as Bluetooth Low Energy, NFC or a QR code. This spec will not mandate which underlying technologies must be supported.

The term local communication refers to data communication over the local communication medium.

The term communication medium topology refers to the composition of the local communication medium which may include sensitive information such as IP or other address information or the number of devices connected to the medium.

3. Permission Policy Integration

The Local Peer-to-Peer API defines a policy-controlled feature identified by the token "local-peer-to-peer". Its default allowlist is "self".

Workers (dedicated and shared) adhere to the permission policy set by their owning document(s):

  • Dedicated workers can be created from other workers, in which case the permission policy of the first owning document (in case of a dedicated worker) or owning documents (in case of a shared worker) up the owner chain will be used.
  • Shared workers often have multiple owning documents as they can be obtained by other documents with the same origin. In this case, all owning documents must be allowed to use the policy-controlled feature defined by this specification.

Note: There has been discussion on allowing setting permission policy directly on a worker on creation, in which case that would have to be consulted as well.

The default allowlist of "self" allows usage in same-origin nested frames but prevents third-party content from using the feature. Third-party content usage can be selectively enabled by adding allow="local-peer-to-peer" attribute to the frame container element:

<iframe src="https://third-party.com" allow="local-peer-to-peer"/></iframe>

Alternatively, the Local Peer-to-Peer API can be disabled completely by specifying the permissions policy in a HTTP response header:

Permissions-Policy: local-peer-to-peer=()

See [PERMISSIONS-POLICY] for more details.

4. Peer Management

Note: This section and its subsections use RFC 2119 terminology in a relaxed manner. These sections will be converted into well-defined algorithmic normative prose informed by further implementation experience. For now, this relaxed description better allows for rapid prototyping.

The user agent is in charge of managing peers.

A peer is an equal participant in the local communication. These nodes can communicate without the need for a central coordination by a server.

A user agent has an associated local peer-to-peer manager in charge of managing peers. Its responsibility is to start local peer discovery, establish local peer connections and acquire a local peer grant on a per-origin basis. This is done to avoid exposing information about the communication medium topology.

4.1. Local state

The local peer-to-peer manager has:

local trust store

A set of trust anchors, see § 4.4 Peer authentication.

known peers map

An ordered map from peer identity to known peer: a peer the user agent has discovered or had a session with. Whether a known peer is authenticated is not stored; it follows from the local trust store.

peer grants

An ordered map from origin to the set of peer identities that the origin may use.

These are kept consistent:

  • Removing a trust anchor removes the peer grants of peers that are no longer authenticated.

  • Removing a known peer removes it from all peer grants.

  • Clearing an origin’s site data or permissions removes its peer grants.

Note: Peer grants are origin-level while the local trust store is shared by all origins, so that the user doesn’t need to authenticate the same peer again for every origin. Origins are kept apart by the peer grants and by the requesting origin of each session. Peer grants could be stored as the origin’s permission data in the permission store, as Web Bluetooth does for its allowed devices.

Validate that a local trust store shared by all origins is appropriate, or whether trust anchors should be partitioned, for example per top-level site. [WICG/local-peer-to-peer Issue #24]

The user agent may persist its local trust store, known peers and/or peer grants. If the user agent chooses to do so, it must do so in accordance with the persistent state rules of the transport binding in use. Such state is said to be persisted. Results of discover peers, such as addresses, are not part of this state. The user agent should let the user view and remove trust anchors, known peers and peer grants.

4.2. Peer advertisement

The user agent can make itself discoverable by advertising, using start advertising.

Note: The user agent must get the user’s explicit consent in order to start advertising.

When advertising, the user agent must listen for incoming peer connections. In case an incoming session is received, the peer is added to the known peers map. The user agent must not directly provide access to the incoming peer connection to any origin. Instead, the user agent must prompt to grant peer access to the origin that initiated peer advertisement.

The user agent must deliver an incoming session only to a started LP2PReceiver that allows the session’s requesting origin, and close the session if there is none. An LP2PReceiver allows an origin if that origin is same origin with the receiver’s relevant settings object’s origin, or with the origin of an entry of its allowedOrigins.

4.3. Peer discovery

When asked to start local peer discovery, the user agent runs discover peers.

If a peer is discovered, the user agent should add it to the known peers map. The user agent must never expose the full result of peer discovery with an origin. Instead, the user agent must acquire a local peer grant to grant access to a peer for the origin that initiated the peer request.

4.4. Peer authentication

A trust anchor is a key that the user agent trusts to authenticate peers. It has:

key

The key that peers' credentials chain to. What the credentials are, and how they chain to a key, is defined by the transport binding.

scope

Either one peer, a single peer that the anchor vouches for, or vouching, any peer the anchor vouches for, within limits defined by the transport binding.

Adding a vouching trust anchor removes the one peer trust anchors with the same key, which it covers.

A trust anchor is added to the local trust store only by a trust ceremony: a run of authenticate a session in which the user takes part, for example by entering a PIN or scanning a QR code. A trust ceremony with a peer adds a trust anchor scoped to one peer: that peer. A vouching trust anchor is only added by a trust ceremony with the vouching party itself.

A peer is said to be authenticated when its credentials chain to the key of a trust anchor in the local trust store, and the peer is within that anchor’s scope.

A peer’s credentials may change over time without changing its peer identity, as long as they chain to the same key. Whether a key can be replaced with continuity is defined by the transport binding; if so, the new key replaces the old one in every trust anchor that has it. Otherwise, a new key needs a new trust ceremony.

Define how a peer can move to another trust anchor’s key while keeping its peer identity and peer grants, for example by proving that it holds both keys.

When asked to authenticate a local peer, the user agent must establish a session with the peer, unless one exists, and run authenticate a session on it. The peer is authenticated if this succeeds.

  • A device paired directly that uses its own key, which makes it self-anchored: its key, scoped to one peer, that device.

  • A device paired directly whose credentials are issued by a hub: the hub’s key, scoped to one peer, that device. The device’s credentials can rotate freely, and other devices of the hub are not trusted.

  • A hub the user chose to trust for its devices, through a trust ceremony with the hub: the hub’s key, scoped to vouching. It replaces the one peer anchors for that hub’s devices, which keep the same peer identity. Removing it removes trust in all of the hub’s devices.

Note: Trust anchors may also be used to validate HTTPS servers on the local communication medium, each constrained to a namespace of local names; see the separate Local HTTPS draft.

4.5. Peer grant

The user agent, with the user’s consent, must acquire a local peer grant for an origin to get access to a peer.

Note: The user agent must get the user’s explicit consent in order to grant an origin access to a peer. For enhanced privacy protection, the user agent must provide means to dismiss any related user interface and this action must not be detectable by script or have script-observable side-effects. The user interface may provide means to revoke the grant or to make the grant persisted.

When asked to acquire a local peer grant, the user agent displays the known peers to the user through its native user interface. When the user selects a peer from the user interface, the user agent must check the selected peer is authenticated, and run the authenticate a local peer algorithm otherwise, and, if the user grants access, add the selected peer’s peer identity to the origin’s peer grants.

5. Transport abstraction

The API and its algorithms are defined against the abstract concepts and operations in this section. A transport binding defines how a concrete protocol implements them. This specification defines one transport binding, in § 12 Binding to the Open Screen Network Protocol. Which bindings a user agent implements is implementation-defined. A peer is associated with the binding through which it was discovered or through which its session arrived, and all operations involving that peer use that binding.

A transport binding must provide end-to-end confidentiality and integrity for all communication with a peer, including when the path to the peer goes through an intermediary.

5.1. Peers and sessions

A peer has the following, provided by its transport binding. None of them is exposed to an origin.

peer identity

An opaque value that identifies the peer, stable across sessions, scoped to the transport binding. It is derived from the key that the peer’s credentials chain to and the peer’s subject under it; for a self-anchored peer, the subject is its own key. It is only trusted once the peer is authenticated. The known peers map and peer grants are keyed on it.

display name

A name for the peer device, for display in user agent user interface, or null. It is asserted by the peer’s user agent, not by script. Trusted only if obtained after the peer is authenticated, or by other means the user agent considers trustworthy; otherwise, such as during discover peers, it is a display hint.

nickname

The nickname given by the remote page when it started advertising, or null. It is chosen by script and never verified.

A Local Peer-to-Peer session is a confidential connection with one peer. It is authenticated if the credentials the peer presented in it chain to a trust anchor in the local trust store, which verifies the peer identity of the peer for it.

A Local Peer-to-Peer session that is exposed to an origin is not shared with other origins. A binding may carry several sessions with the same peer over one underlying connection, or use a separate connection for each.

For each Local Peer-to-Peer session, the side that established it with establish local peer connection is the client, and the side that reported it as an incoming session is the server. Once established, the session is symmetric: either side can use any operation on it, except that:

  • the server validates the requesting origin;

  • where the binding needs it to avoid collisions, identifiers such as ids and streams follow the role;

  • only the client opens any additional underlying connection for the session.

A Local Peer-to-Peer session that is exposed to an origin has a requesting origin: the origin on whose behalf the client established it. The client conveys it inside the authenticated session, bound to that session (for example by a per-origin credential or the exporter context; defined by the transport binding). The server checks it as described in § 4.2 Peer advertisement.

The requesting origin is asserted by the peer’s user agent. The binding guarantees that it is consistent for the session, not that it is authentic: it does not prove that the remote page was served by that origin. User agents must not grant anything that belongs to the requesting origin, such as its permissions, storage or credentials, on the strength of it. This is the same model as the Origin header in [FETCH].

Device keys, credentials and anything else that would let an origin authenticate as the user agent must not be exposed to origins. User agents should instead expose per-session keying material exporters, like those of WebTransport over HTTP/3, so that applications can prove their origins with credentials their own origin issued.

Define the keying material exporter API, for example an exportKeyingMaterial() method as considered for WebTransport, and whether its context includes the requesting origin.

A data channel is a reliable, ordered, message-preserving, bidirectional channel on a Local Peer-to-Peer session. Either side can open one. It has an id, an integer between 0 and 65,534 that is unique within the session, a label and a protocol. A message on a data channel is a sequence of bytes, marked as either text or binary.

5.2. Operations

A transport binding provides the following operations. Any of them can fail, including because the peer does not support it.

To start advertising given a nickname

Make the user agent discoverable through discover peers on other user agents, with the given nickname if the binding can carry it, and accept sessions from peers. This returns an advertisement. Each Local Peer-to-Peer session a peer establishes with it is reported as an incoming session for that advertisement. To stop advertising given an advertisement ends both.

To discover peers

Report the peers advertising on the local communication medium, as they appear and disappear, until asked to stop discovering peers. A discovered peer identity is not verified.

To establish local peer connection with a peer

Establish a Local Peer-to-Peer session with the peer. On the peer, the session is reported as an incoming session.

To authenticate a session

Mutually authenticate the two sides of a Local Peer-to-Peer session and verify the peer identity of the peer, so that the session is authenticated. If the peer’s credentials do not chain to a trust anchor in the local trust store, this is a trust ceremony, which requires user interaction on one or both devices and adds a trust anchor scoped to that peer. Either side can initiate it.

To open a data channel on an authenticated Local Peer-to-Peer session given a label, a protocol and an optional id

Open a data channel with that label and protocol, and with the given id or, if none is given, one chosen by the binding. The other side is notified of an incoming data channel, which its user agent accepts or refuses. The operation succeeds if it is accepted.

To send data on a channel given a data channel and a message

Queue the message for delivery on the data channel. The other side is notified of a received message.

To close a data channel

Close the data channel in both directions. The other side is notified that it was closed.

To close a session

Close the Local Peer-to-Peer session, all of its data channels and any WebTransport session opened over it. The other side is notified that it was closed. The binding also reports a session as closed when the underlying transport fails.

To open a WebTransport session over an authenticated Local Peer-to-Peer session

Establish a session with the same peer that provides the capabilities of a WebTransport session as defined in [webtransport], bound to the same peer identity. The other side is notified of an incoming WebTransport session.

Note: Data channels (LP2PDataChannel) and WebTransport sessions (LP2PQuicTransport) are two independent ways to communicate over a Local Peer-to-Peer session; neither is built on the other.

Decide whether to keep both data channels and WebTransport sessions, or converge on one. [Issue #29]

6. LP2PReceiver Interface

The LP2PReceiver interface allows advertising on the local communication medium, enabling other peers to discover and connect.

[Exposed=(Window,Worker), SecureContext]
interface LP2PReceiver : EventTarget {
  constructor(optional LP2PReceiverOptions options = {});
  attribute EventHandler onconnection;
  Promise<undefined> start();
};

6.1. LP2PReceiverOptions

dictionary LP2PReceiverOptions {
    DOMString nickname;
    sequence<USVString> allowedOrigins = [];
};
allowedOrigins, of type sequence<USVString>, defaulting to []

A list of URLs whose origins, in addition to the receiver’s own origin, the receiver allows as the requesting origin of an incoming session. By default, only same-origin sessions are delivered.

Decide the granularity of allowedOrigins, the requesting origin and peer grants: per origin or per site, and whether to allow wildcards or any origin.

6.2. LP2PConnectionEvent

In general, when defining a new interface that inherits from Event please always ask feedback from the WHATWG or the W3C WebApps WG community. See defining event interfaces.

[Exposed=(Window,Worker), SecureContext]
interface LP2PConnectionEvent : Event {
    constructor(DOMString type, LP2PConnectionEventInit connectionEventInitDict);
    readonly attribute LP2PConnection connection;
};

dictionary LP2PConnectionEventInit : EventInit {
    required LP2PConnection connection;
};

6.3. Events

The following event is fired at the LP2PReceiver object:

Event name Interface Fired when…
connection LP2PConnectionEvent An incoming connection is received.

6.4. Event handlers

The following are the event handlers (and their corresponding event handler event types) that must be supported, as event handler IDL attributes, by all objects implementing the LP2PReceiver interface:

event handler event handler event type
onconnection connection

6.5. Examples

Example: Setting up a receiver to listen for connections:

const receiver = new LP2PReceiver({
    nickname: "example-receiver",
});
receiver.onconnection = e => {
    console.log("Connection established!");
    const conn = e.connection;
};

// Blocks until permission is received.
await receiver.start();

9. The LP2PDataChannel Interface

The LP2PDataChannel interface represents a bi-directional data channel between two peers. An LP2PDataChannel is created via a factory method on a LP2PConnection object. It is backed by a data channel on the connection’s Local Peer-to-Peer session.

Note: The LP2PDataChannel interface is purposefully kept as close as possible to the RTCDataChannel interface defined in [webrtc]. The aim is to allow seamless transition of developers that are familiar with WebRTC as well as allowing libraries to easily work with both the [webrtc] and LP2P API.

[Exposed=(Window,Worker), SecureContext]
interface LP2PDataChannel : EventTarget {
  constructor(USVString label,
              optional LP2PDataChannelInit dataChannelDict = {});
  readonly attribute USVString label;
  readonly attribute USVString protocol;
  readonly attribute unsigned short? id;
  attribute EventHandler onopen;
  attribute EventHandler onerror;
  attribute EventHandler onclosing;
  attribute EventHandler onclose;
  undefined close();
  attribute EventHandler onmessage;
  attribute BinaryType binaryType;
  undefined send((USVString or Blob or ArrayBuffer or ArrayBufferView) data);
};

9.1. LP2PDataChannelInit

dictionary LP2PDataChannelInit {

9.8. Examples

Example: Receive a LP2PDataChannel on an existing connection as receiver:

const receiver = new LP2PReceiver({
    nickname: "example-receiver",
});

receiver.onconnection = e => {
    const conn = e.connection;
    console.log("Receiver: Got a connection!");

    conn.ondatachannel = e => {
        const channel = e.channel;

        channel.onmessage = e => {
            const message = e.data;
            console.log(`Receiver: Received message: ${message}`);

        channel.send("Good day to you, requester!");

    nickname: "example-request",
});

const conn = await request.start();

const channel = conn.createDataChannel("My Channel");

channel.onopen = e => {
    channel.onmessage = e => {
        const message = e.data;
        console.log(`Requester: Received message: ${message}`);
    };

    channel.send("Good day to you, receiver!");
};

dictionary LP2PQuicTransportListenerInit {
};

10.2. Examples

Example: Setting up a request for a LP2PQuicTransport:

const request = new LP2PRequest({
    nickname: "example-request",
});

const transport = new LP2PQuicTransport(request);

// Blocks until transport is ready.
await transport.ready;

Example: Receiving a LP2PQuicTransport:

const receiver = new LP2PReceiver({
    nickname: "example-receiver",
});

const listener = new LP2PQuicTransportListener(receiver);

for await (const transport of listener.incomingTransports) {
  // Blocks until transport is ready.
  await transport.ready;
}

Refer to the WebTransport examples for usage of a [webtransport] object.

11. Security and privacy considerations

11.1. Transport bindings

The security and privacy considerations of the protocol underlying the transport binding in use must be considered when implementing this API. For § 12 Binding to the Open Screen Network Protocol, these are the Security and Privacy considerations of the Open Screen Network Protocol.

11.2. Personally identifiable information

The peer attributes, such as the nickname and device model, are provided to give minimal context to a connected peer. This information could be used in conjunction with other information for fingerprinting the user. However, this information is only available to an origin after it has been authenticated and a user has given explicit consent to make the connection to the remote peer.

No information is exposed to the origin during service discovery. No IP information is exposed to an origin. This is fully managed by the user agent.

Refine the peer attributes exposed to origins. [WICG/local-peer-to-peer Issue #15]

11.3. User interface guidelines

When the user is asked to grant permission to connect to a peer, the user agent should make it clear what origin the request is coming from.

Define peer filtering to give the user additional context. [WICG/local-peer-to-peer Issue #15]

11.4. Impact on same-origin policy

This document extends the Web platform with the ability to set up real-time, direct communication between browsers and other devices, including other browsers, within a local communication medium.

This means that data and media can be shared between applications running in different browsers, or between an application running in the browser and another user agent that is not a browser such as a headless service provided by a smart TV or smart fridge. This extends the usual barriers in the Web’s security model that prevents sending data between entities with different origins.

To limit this, a session is only delivered to an LP2PReceiver of the same origin as its requesting origin, unless the receiver opts in to other origins with allowedOrigins. The requesting origin is asserted by the peer’s user agent, so a peer can claim any origin; but a lying peer can only be one the user already authenticated and trusts with what they send it.

11.5. Device Access

The Local Peer-to-Peer API requires user permission for a page to access any peers. The API uses purpose-fit protocols for data communication. It cannot be used to connect to raw sockets or unknowing HTTP servers. In addition, a user must acquire a local peer grant by explicitly providing consenting for an origin to connect to a peer. In addition, a user must authenticate a local peer before use.

11.6. Persistent State

The persistent state rules of the transport binding in use must be followed when implementing this API. For § 12 Binding to the Open Screen Network Protocol, these are the Open Screen Network Protocol Persistent State rules.

11.7. Secure Contexts

The Local Peer-to-Peer API must only be provided in a secure context.

12. Binding to the Open Screen Network Protocol

This section defines a transport binding to the Open Screen Network Protocol (OSP). In this binding, a peer is an OSP agent and a Local Peer-to-Peer session is an authenticated QUIC connection between two agents.

To discover metadata of an agent, the user agent follows Open Screen Network Protocol transport and metadata discovery.

The concepts and operations of § 5 Transport abstraction map onto OSP as follows:

display name The display name from the agent-info-response message, obtained by discover metadata

Part of these operations are defined below as protocol extensions to the Open Screen Network Protocol.

12.1. Data channel extension

In order to signal support for this protocol extension, the agent should include the data-channels agent-capability as part of the agent-info-response message exchanged during discover metadata.

To open a data channel, an agent may send a data-channel-open-request message on a new QUIC stream. The Local Peer-to-Peer session must be authenticated. The message must contain the following values:

channel-id

An ID number between 0 and 65,534 which uniquely identifies the data channel. When the binding chooses the id, the client uses an even number and the server an odd number. The value 65,535 is reserved, as for RTCDataChannel; id is an unsigned short for parity with id, but cannot take that value.

label

a string that contains a name describing the data channel. These labels are not required to be unique.

protocol

a string containing the name of the subprotocol in use. If no protocol was specified when the data channel was created, then this property’s value is the empty string ("").

The receiving agent reports the data-channel-open-request as an incoming data channel. When the receiver receives the data-channel-open-request, it should send back a data-channel-open-response message. The response must include the following:

result

a code indicating success or failure, and the reason for the failure. If the user agent refuses the incoming data channel, the result indicates failure.

If the data-channel-open-response message indicates success, the data channel is considered open. Agents can now send data on a channel by sending data-frame messages (type key 24) on the same QUIC stream the data channel was opened. The message must include the following keys; the other keys of data-frame (1, 2, 3 and 5) are unused, should not be sent, and must be ignored by the receiving agent:

encoding-id

Determines the encoding of the data being sent. The values are specified as data-channel-encoding-id, instead of referencing a data encoding offer: 0: Blob; 1: String; 2: ArrayBuffer.

payload

The binary representation of the data being sent.

A text message is sent with String; a binary message with Blob or ArrayBuffer. The receiving agent reports each data-frame as a received message, which is text if its encoding-id is String and binary otherwise.

12.2. WebTransport extension

The protocol extension to send data on a channel provides an ergonomic way to send simple messages. An agent can open a WebTransport session for communication that requires low overhead and more granular streams control.

In order to signal support for this protocol extension, the agent should include the quic-transport agent-capability as part of the agent-info-response message exchanged during discover metadata.

To open a WebTransport session, the client of the Local Peer-to-Peer session dials a new QUIC connection using the agent certificates established during authenticate a session. During connection establishment, the ALPN token "q2q" must be used in the TLS handshake.

The capabilities of the Local WebTransport session are defined in [webtransport].

Note: The WebTransport-over-QUIC protocol is yet to be defined. Potentially considering earlier work such as draft-vvv-webtransport-quic.
